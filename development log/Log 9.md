# Day 9 — The Quality Sanding

**Phase:** Output Polish & Structural Overhaul

**Focus:** Fixing formatting inconsistency between model providers, restructuring the document's heading hierarchy, and integrating the user's personal note-taking style into the generated output.

**Duration:** 6 hours

---

# Overview

Day 8 ended with the 1000-word ceiling broken — test outputs hit 6,371 to 12,000 words. The throughput problem was solved. But the output had a visible "two formatting eras" problem: early topics used plain `### Why it matters` headers with inline callouts, while later topics used emoji-prefixed `### 🏗️ How It Works` headers with bold-title callouts. The teaching model's fallback chain (OSS-120B → Llama-3.3-70B → Gemini Flash Lite) was producing different formatting from each provider, and the structural prompts were too rigid.

The day was spent sanding every rough edge — 6 rounds of changes across 5 prompt files and 2 service files, with 5 test outputs generated and analyzed.

# Round 2: Teaching Prompt STRUCTURE Overhaul

**Problem:** The STRUCTURE section said "Start with WHY this matters before HOW it works" and "End by connecting to what comes next." The model literalized both — every section opened with `### Why it matters` and ended with a formulaic "So, how do we actually..." bridge sentence. This produced a rigid template that made the notes feel like a fill-in-the-blank worksheet.

**Fix (3 edits to `teaching.py`):**

1. **Softened the scaffold:**
   - `Start with WHY this matters` → `Open with the motivation or intuition before diving into mechanics. Don't label it "Why it matters" — just write it naturally.`
   - Added: `Pick sub-headings that fit the specific topic, not the same generic ones every time. Vary your structure.`

2. **Made forward transitions optional:**
   - `End by connecting to what comes next` → `A forward transition to the next topic is optional. Don't force one if it feels unnatural.`

3. **Unified callout format with a worked example:**
   - Added explicit bold-title convention: `> [!type] **Bold Title Here**` on line 1, `> The body text goes on the next line with its own > prefix.`
   - Every callout type now shows the bold-title format: `> [!note] **Extra context or side notes**`

**Result:** Later test outputs showed varied subheadings (`### 💡 The Intuition`, `### 🏗️ How It Works`, `### 📝 Worked Example`) instead of the rigid template. Callouts were 100% consistent with the bold-title convention.

# Round 3: Nav Bar — Source Grouping → Subject Grouping

**Problem:** The nav bar was originally generated by the LLM (inline pipe-separated links with inconsistent formatting). I replaced it with programmatic heading extraction (flat bullet list), which eliminated formatting drift. But the user wanted the nav bar grouped by subject area (Part I: Linear Regression, Part II: Logistic Regression), not flat.

**First attempt — Source-based grouping:** I passed source boundaries (video titles, file names) from `pipeline_service.py` to `merge_sections()` and built a grouped nav bar with `### Part N: Source Title` dividers. This produced ugly part labels like `### II: https://youtu.be/yIYKR4sgzI8?...`.

**Second attempt — Subject-based grouping via LLM:** Reverted the source-based approach and modified `document_structure.py` to generate a grouped TOC by subject area. The LLM reads the full document and clusters related `##` headings into parts with Roman numerals. Added paired regex markers (`---TOC---`/`---ENDTOC---`) for robust parsing.

**Decision rationale:** Source grouping is deterministic but wrong — it splits related topics across different parts. Subject grouping requires semantic understanding, which only an LLM can provide. The document_structure call uses Gemini Flash Lite (single model, no formatting drift), so the TOC formatting is consistent.

# Round 4: Bridge Sentence Ban

**Problem:** Despite the STRUCTURE change making transitions optional, the model still ended most sections with "So, how do we actually..." variants. The pattern was deeply ingrained.

**Fix (teaching.py):**
```
Avoid starting every final paragraph with "So, how do we actually..."
→ Never start one with "So, how do we" — with or without "actually".
Also avoid "So how does", "So what does", "So once you've".
```

**Later widened (Round 7):** Changed to "Never start one with 'So, how do we' — with or without 'actually'" after test55 and test56 still showed the pattern.

# Round 6: H1 Part Dividers + Subheading Renumbering

**Problem:** The user wanted the heading structure to match their personal notes — part dividers as `# ▣ Part I: Title` with numbered subheadings like `### 1.1 — Subtitle`. The initial grouped TOC put part labels only in the nav bar, not in the document body.

**Implementation:**

`_parse_toc_parts(toc_text)`: Parses the LLM's grouped TOC into structured `[(part_num, part_label, [headings]), ...]` tuples using regex on `### Part (ROMAN): Title` and `- [[#Heading]]` patterns.

`_insert_part_dividers(merged, parts)`: Walks the document line by line. When it encounters the first `##` heading of a new part, inserts:
```

---
# ▣ N: Part Title
---

```

Then renumbers each `### Subheading` sequentially within the part as `### N.1 — Original Subheading`.

**Fallback path:** If the LLM's TOC parsing fails, falls back to flat programmatic nav bar with no dividers or renumbering.

# Key Decisions Made Today

1. **LLM grouping over programmatic grouping for TOC:** Subject grouping requires understanding content semantics, which only an LLM can do. Used Gemini Flash Lite (single model, no drift) for the document_structure call.

2. **Post-processing over stronger prompts for nav header level:** The LLM ignores "MUST" instructions sometimes. A one-line `replace()` is more reliable than another prompt sentence.

3. **Paired regex markers over line-by-line parsing:** `---TOC---`/`---ENDTOC---` with `re.DOTALL` is more robust than iterating lines looking for section starts.

4. **All additive changes, never subtractive:** Every prompt edit added instructions rather than removing them. Existing working behavior was preserved.

5. **Kept emoji heading style over numbered sections:** The user's notes use `### 1.1 -- Title` WITH emojis. The HAS output already had emoji-prefixed headings, so we kept that and just prepended the numbering.

# Session 2 — The Divider Fix (Post-Log)

**Duration:** ~40 min

**Problem:** `_insert_part_dividers()` only matched `## ` (H2) headings for divider insertion, but all teaching sections use `### ` (H3) for their topic headings. The method never fired for any document. The `## ▣ I:` dividers visible in test56–test59 were from the LLM's document_structure response, not from the code.

**Fix — heading-level matching (line 330):**
```
# old: stripped.startswith("## ") and not stripped.startswith("### ")
# new:
heading_match = re.match(r"^(#{2,3})\s+(.+)$", stripped)
```
This matches both `## Title` and `### Title`, while treating both as valid divider anchor points.

**Fix — renumbering guard (line 346–353):**
```
# old: any ### heading when current_part > 0 gets renumbered
# new: only ### headings NOT in heading_to_part get renumbered
```
Topic headings (which are in the TOC's `heading_to_part` dict) stay as-is. Only subheadings within topics get the `N.M —` prefix.

**Fix — TOC divider stripping (merge_sections, line 417):**
```
toc_lines = [l for l in toc_text.split("\n") if "\u25a3" not in l]
```
The LLM's document_structure response often includes `## ▣` dividers inside the TOC markers. Without stripping, these would duplicate the code-generated `# ▣` dividers. Stripping by `▣` character removes them before prepending.

**Verification:** Unit tests with both `##` and `###` heading styles confirmed:
- Dividers inserted at `# ▣ N: Title` before each part's first topic heading
- Topic headings preserved (not renumbered)
- Subheadings renumbered as `### N.M — Original Title`
- No duplicate dividers when TOC already contains `▣` lines
- `\boxed{}` confirmed in test58 (line 325) and test59 (line 91)

**Outstanding:** `[!abstract]` still unused. Likely content-dependent (no pipeline summaries in recent test inputs). Not urgent.

# Lessons Learned

1. **Subject-based grouping requires an LLM.** No amount of programmatic string matching can determine whether "Log Odds" belongs under "Foundations" or "Logistic Regression." The LLM needs to read the content.

2. **A single TOC format can't serve both short and long documents.** For 200-line outputs the TOC lists `##` content headings neatly under parts. For 900-line outputs the LLM includes `###` subheadings too, breaking the heading-level matching in divider insertion.

3. **Prompt instructions have diminishing returns.** "NEVER" and "MUST" are no more effective than "avoid" and "should." The model's training data patterns often overpower prompt directives. Post-processing catches what prompting can't.

4. **The user's personal note style is the reference standard.** Every structural decision (H1 dividers, numbered subheadings, `\boxed{}`, comparison tables) was validated against what the user actually writes in their own notes. This grounded the changes in real usage rather than abstract "best practices."

5. **Additive prompt changes are safer than deletions.** Every new instruction was layered on top of existing ones. If a change doesn't work, you can still produce the old output. If you delete something, you can't get it back without reverting.

6. **The 1000-word ceiling is dead.** test57.md hit 11,412 words from a 3.5-hour lecture. The merge concatenation approach (concatenate + transitions + ToC/glossary, no hierarchical rewrite) is the permanent fix.
